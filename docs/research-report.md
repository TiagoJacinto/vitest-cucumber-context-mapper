# Research report: TypeScript content mappers for Gherkin

Research verified against primary sources on 2026-10-23. Version and maturity statements are time-sensitive.

## Findings at a glance

- TypeScript content mappers are available in the 7.1 beta line. At the time of this research, npm reported stable 7.0.2, beta 7.1.0-beta, and next 7.1.0-dev.20261023.1. TypeScript 7.1 had not reached its planned stable release date. The content-mapper API was on the 7.1 stabilization plan. [TypeScript versions](https://www.npmjs.com/package/typescript?activeTab=versions), [7.1 iteration plan](https://github.com/microsoft/TypeScript/issues/63703), [7.1 beta announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)
- A mapper is an external process selected from a project’s tsconfig. The compiler requests transformed TypeScript and span mappings; the mapper does not need to emit a declaration sidecar. CLI use requires the explicit --runExternalCode switch. [Merged content-mapper proposal, PR 4712](https://github.com/microsoft/typescript-go/pull/4712), [current TypeScript mapper implementation](https://github.com/microsoft/TypeScript/tree/main/tsc/internal/contentmapper)
- The general SDK ts-content-mapper 0.1.0 has the smallest suitable abstraction found: current protocol types, a project-aware JSON-RPC runner, and a UTF-8/UTF-16 span-mapping builder. It is very new, so pin it and isolate it behind a transport adapter. [SDK package manifest](https://raw.githubusercontent.com/sxzz/ts-content-mapper/main/package.json), [SDK README](https://github.com/sxzz/ts-content-mapper), [mapping tests](https://github.com/sxzz/ts-content-mapper/blob/main/tests/mappings.test.ts)
- vitest-cucumber 8.0.0 has runtime validation, but its public callback types accept plain strings. It uses its own line-oriented parser rather than @cucumber/gherkin. A paired content mapper and Vite runtime transform can expose typed functional scenario/step constructors directly from a static `.feature` import, avoiding both a generic type argument and a loader call. [Pinned upstream package](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/package.json), [loader](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/load-feature.ts), [public callback types](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/types.ts)
- The TypeScript mapper and the Vitest Cucumber runtime must be treated as separate parsers until their outputs are compared. The official parser preserves full Gherkin AST structure and positions; the current runtime parser has narrower and observably different behavior. The first integration slice should stay within constructs both accept.

## TypeScript protocol and lifecycle

The accepted protocol is described in PR 4712 and updated by later TypeScript changes. Projects register a package and the foreign extensions it handles in a root-level contentMappers array. TypeScript resolves the package and starts the executable declared under package.json → typescript → contentMapper → exec. The manifest can also declare compilerOptions used by a transform’s identity and dynamicConfig when the mapper depends on configuration beyond the passed options. [PR 4712](https://github.com/microsoft/typescript-go/pull/4712), [TypeScript PR 63936](https://github.com/microsoft/TypeScript/pull/63936)

TypeScript is the JSON-RPC client. It sends initialize, openProject, transform, and closeProject requests over stdio. A process can serve several projects; an opaque projectHandle ties transforms to the relevant project state. initialize negotiates UTF-8 or UTF-16 positions. openProject supplies mapper options and effective compiler options. A dynamic mapper can return a stable configIdentity and watchedFiles. transform receives the original file contents and returns virtual code, a TypeScript-family extension, optional mappings, parser diagnostics, and optional supplemental outputs. [Protocol definition in PR 4712](https://github.com/microsoft/typescript-go/pull/4712), [SDK server](https://github.com/sxzz/ts-content-mapper/blob/main/src/server.ts)

Span mappings use virtual start/length, original start/length, a mapping kind, and optional language-service feature flags. Verbatim spans preserve text and length; atom spans relate spans that can differ; alias spans identify different spellings of the same logical name. Virtual gaps are generated text and have no source location. TypeScript can project diagnostics through mappings; edit-producing language-service actions can write back only through exact verbatim spans. [Span-map description](https://github.com/microsoft/typescript-go/pull/4712), [current span-map implementation](https://github.com/microsoft/TypeScript/tree/main/tsc/internal/spanmap)

The compiler requires --runExternalCode before it executes a configured mapper. In VS Code, mapper execution is limited to trusted workspaces. TypeScript’s language server registers mapped-file requests and projects supported requests through spans. This prototype verified that path with a headless TypeScript 7.1 LSP client: it registered `.feature` synchronization, diagnostics, hover, and definition; mapped hover returned the scenario’s virtual metadata at the source title; and a malformed in-memory edit produced a source-positioned Gherkin diagnostic. That does not verify a user-facing editor extension, completion, navigation, or formatting experience.

Use an explicit extension in imports, such as `import * as checkoutFeature from "./checkout.feature"`: registered mapper extensions are not searched for extensionless imports. The relevant TypeScript issue was closed as not planned, so this is the current resolver boundary, not an outstanding bug report. Another open suggestion notes that the LSP registers formatting requests for mapped extensions even when a mapper cannot provide useful formatting; no Gherkin formatting support is claimed here. [LSP implementation at the pinned compiler commit](https://github.com/microsoft/TypeScript/blob/a91e93821feafd081641f9f5d161eba626d0b2ce/tsc/internal/lsp/server.go), [extensionless lookup issue 64546](https://github.com/microsoft/TypeScript/issues/64546), [formatter registration issue 64579](https://github.com/microsoft/TypeScript/issues/64579)

Incremental and build modes record mapper identities in tsbuildinfo. Static identities include the resolved package/version, tsconfig mapper options, and declared compiler options. A dynamic mapper provides its own identity and watch set. Changing a local mapper without changing its package version may not invalidate an incremental build; the TypeScript proposal recommends bumping the version or forcing/cleaning the build. [Incremental behavior in PR 4712](https://github.com/microsoft/typescript-go/pull/4712)

For reliable resolution, use explicit `.feature` module paths. Current TypeScript does not probe registered custom mapper extensions for extensionless relative imports under bundler resolution. This behavior is closed as intended. [Issue 64546](https://github.com/microsoft/TypeScript/issues/64546)

## Mapper implementation options

| Option | Correctness and compatibility | Maintenance and dependencies | Complexity, tests, and mappings | Assessment |
|---|---|---|---|---|
| A. ts-content-mapper SDK | Tracks the current protocol types and process lifecycle. It is still an early 0.1 release, and TypeScript 7.1 is beta-era. Pin both compiler and SDK. | One runtime dependency, vscode-jsonrpc. Requires Node ^22.18.0 or >=24.11.0. | Lowest implementation burden. Includes lifecycle and mapping code plus UTF-8/UTF-16 mapping tests. Mapping builder covers verbatim, atom, alias, anchor, and lower-level spans. | Recommended for the prototype behind an adapter. Replaceable if protocol changes or the SDK stops tracking TypeScript. |
| B. Implement the protocol directly | Maximum local control, but every wire detail and future protocol change becomes our responsibility. | Could use vscode-jsonrpc directly, but would still own request dispatch, project handles, cancellation, mapping encoding, and compatibility. | More code and more ways to drift. We would need our own tests for framing, lifecycle, cancellation, encoding, and mapping invariants. | Not justified for the first vertical slice; reconsider only if SDK constraints are demonstrated. |
| C. Adapt a mature content mapper | Existing MDX, CSS Modules, and Astro mappers show useful patterns but implement different formats and semantics. | MDX brings a broad Markdown/MDX dependency graph; Astro depends on Astro transforms; CSS Modules depends on PostCSS tooling. Their implementations are not general Gherkin adapters. | Their mapping and parser tests are useful examples. Reusing their full parsers/generators would add unrelated dependencies and couple this project to their format. | Reuse design and test patterns, not their implementation. |

The current repositories show active experimentation, not equivalent maturity. mdx-content-mapper 0.0.2 has a substantial test suite and MDX-specific mappings; css-modules-content-mapper 0.2.0 tests PostCSS-derived exports and mappings; @astrojs/ts-content-mapper 0.2.0 builds on Astro’s transform pipeline and supplemental script outputs. None should be treated as a generic Gherkin base. [MDX source and tests](https://github.com/remcohaszing/mdx-content-mapper), [CSS Modules source and tests](https://github.com/remcohaszing/css-modules-content-mapper), [Astro mapper package](https://github.com/withastro/astro/tree/main/packages/language-tools/ts-content-mapper)

### Selection

Use ts-content-mapper 0.1.0 for the first implementation, pin its exact version, and isolate it in the protocol adapter. Keep the parser and generator independent of the SDK. Its tests cover the SDK's own lifecycle and mapping builder, but its package development dependencies target TypeScript 6.0 plus a TypeScript 7.0 native-preview alias, not the 7.1 beta. Therefore those tests do not establish end-to-end compatibility with the compiler version required here; the real compiler acceptance test in this repository is essential. Its young age and the TypeScript beta surface make the adapter boundary and reproducible lockfile necessary. This follows the user's preference for the smallest reliable abstraction rather than selecting a dependency based on release recency alone. [SDK package manifest](https://raw.githubusercontent.com/sxzz/ts-content-mapper/main/package.json)

## Vitest Cucumber architecture and current validation

The inspected upstream release is @amiceli/vitest-cucumber 8.0.0 at commit c4b6652f20bcc1065a4532ead064bc45e54fc78d. Its package requires Vitest ^5.0.0. The README’s older statement that v3.4.4 requires Vitest >=2 does not reflect the current package manifest. [Package manifest](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/package.json), [README](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/README.md)

loadFeature reads lines into the project’s own GherkinParser and returns its Feature model; loadFeatureFromText exposes the same parser for in-memory text. The parser supports localized keyword tables when the language option is supplied, but it does not select the dialect from a Gherkin language comment. Scenario and step models do not retain source positions. [Loader](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/load-feature.ts), [parser](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/parser.ts), [language parser](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/lang/SpokenParser.ts)

describeFeature registers Vitest suites/tests and validates registrations synchronously during test-file collection. It checks scenario and Rule names against the parsed model. Step matching compares step type and details exactly; predefined expressions add a runtime pattern-matching path. Missing scenarios and steps therefore fail at runtime/test discovery, not TypeScript check time. The public ScenarioTest and StepCallbackDefinition signatures still use string. [describeFeature](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/describe-feature.ts), [scenario step matcher](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/describe/describe-scenario.ts), [types](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/types.ts)

Scenario Outline examples are stored as string-valued records in the runtime model and expanded into tests. Placeholders are substituted into step titles and docstrings; mappedExamples can apply user-provided transformations. The current runtime model represents one examples array per outline. Feature and Rule backgrounds are explicit callback registrations; background steps are restricted to Given and And. Rules, tags, docstrings, tables, and parameterized steps are supported, but the type declarations do not infer outline variables or step expression parameters. [Scenario model](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/models/scenario.ts), [outline runner](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/vitest/describe/describe-scenario-outline.ts), [background model](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/models/Background.ts)

The optional Vite synchronization plugin watches feature files and uses ts-morph AST helpers to add or remove scenarios and steps in corresponding spec files. It is a source-file synchronizer, not a TypeScript content mapper or compile-time validation mechanism. [Plugin](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/plugin/index.ts), [feature AST updater](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/plugin/ast/FeatureAst.ts)

The inspected package exports that Vite plugin and its runtime APIs; it has no TypeScript content-mapper or tsserver-plugin implementation. This prototype can therefore remain an optional companion without changing the library.

An isolated clone of this upstream version passed its own npm run test:unit and npm run build checks during research: 40 test files, 570 tests passed, 22 skipped, and declaration generation succeeded. The upstream suite covers parser, outline, expression, background, Rule, tag, and plugin behavior; no use-site compile-time assertion suite was found. This is an upstream test result, not a test of the prototype in this repository.

## Official Gherkin and Messages

The verified JavaScript packages are @cucumber/gherkin 42.0.1 and @cucumber/messages 34.2.1. Gherkin provides Parser, AstBuilder, token matchers, and compile(). Its AST preserves Features, Rules, scenarios/outlines, steps, backgrounds, Examples, tags, tables, docstrings, and source locations. @cucumber/messages supplies the AST/Envelope/Pickle/Location data model and ID generators; it does not parse Gherkin or connect steps to application callbacks. [Gherkin JavaScript README](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/README.md), [Parser source](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/javascript/src/Parser.ts), [AST builder](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/javascript/src/AstBuilder.ts), [Pickle compiler](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/javascript/src/pickles/compile.ts), [Messages types](https://github.com/cucumber/messages/blob/03398dca51f443fbc3cf2412989cc5a1a02f3891/javascript/src/messages.ts)

Locations in the AST are one-based line and column values. AST is the right source for the type schema because Pickles are execution-oriented expansions: each Examples row creates a Pickle, backgrounds become executable steps, and inherited tags are added. A mapper should retain the AST’s scenario outline and Examples structure instead of treating expanded Pickles as authored scenarios. Gherkin table cells and example values are strings; numeric or boolean inference would be unsound without a separately specified conversion rule. [Gherkin AST documentation](https://github.com/cucumber/gherkin), [Pickle compiler](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/javascript/src/pickles/compile.ts), [Messages types](https://github.com/cucumber/messages/blob/03398dca51f443fbc3cf2412989cc5a1a02f3891/javascript/src/messages.ts)

## Runtime parity risks

The two parsers agree on the simple English feature used for the initial vertical slice, but the official parser’s broader grammar must not automatically be advertised as accepted by the Vitest Cucumber runtime.

- Official Gherkin honors a # language: header. Vitest Cucumber’s parser uses its language option and ignores comment lines, so localized runtime parsing needs an explicit option.
- Official AST supports multiple Examples blocks per outline. The current Vitest Cucumber model uses one examples array. Source inspection and a smoke run found that a second block can be interpreted incorrectly by the runtime parser.
- Official Pickles include inherited Feature/Rule/Scenario/Examples tags and backgrounds; Vitest Cucumber stores tags on its own model objects and handles backgrounds through explicit callbacks.
- Official AST locations are absent from Vitest Cucumber’s models. Mapper source mappings therefore belong to the content mapper; they cannot be obtained from loadFeature’s result.

These are verified differences from source inspection and parser smoke checks. A typed companion should test parser parity for every construct it exposes, preserve runtime validation, and clearly scope unsupported syntax. [Vitest Cucumber parser](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/parser.ts), [language parser](https://github.com/amiceli/vitest-cucumber/blob/c4b6652f20bcc1065a4532ead064bc45e54fc78d/src/parser/lang/SpokenParser.ts), [official Pickle compiler](https://github.com/cucumber/gherkin/blob/22f215731204768341dc580de292e5302b32e0d6/javascript/src/pickles/compile.ts)

## Integration recommendation

Start with two boundaries:

1. A format-level Gherkin content mapper that parses with @cucumber/gherkin and exports a readonly virtual TypeScript schema, including scenario names, step kind/text, and source locations.
2. An optional Vitest Cucumber companion that adds typed scenario builders and a nested `steps` API, plus a Vite runtime transform that delegates to the existing parser and test-registration API.

No change to the existing @amiceli/vitest-cucumber API is required for this opt-in path. TypeScript still cannot derive a schema from a runtime path string, but the static `.feature` import binds the virtual type signature and runtime constructors to the same source module.

For distribution, keep the generic mapper usable independently and place Vitest-specific wrapper types in a companion package. Avoid requiring TypeScript 7.1 for the runtime-only Vitest Cucumber library. Upstream integration should only follow a working companion prototype and a documented parser-parity policy.

## Verified facts versus open questions

The first callback prototype verified importing a feature-specific callback API, then the design moved to a functional Effect API. The current `.feature` module exports named `run`, literal scenario builders, and a nested `steps` object; the `then` tag is nested because a named `then` export makes the ES module namespace thenable. The paired Vite transform calls the existing synchronous `loadFeatureFromText()` parser and `describeFeature()` API. Feature edits change consumer diagnostics without running Vitest; parser failures map back to `.feature`; mapping tests cover Unicode and LF/CRLF under UTF-8/UTF-16; and the headless LSP returns mapped hover and source-positioned parser diagnostics. The current functional Effect design and verification are documented in [functional-api.md](functional-api.md). The headless LSP probe itself returns success after its assertions, although its child `tsc --lsp` process exits with status 1 and stderr `context canceled` after the accepted shutdown/exit sequence; do not describe that as a clean server shutdown.

Still open: broad workspace-trust coverage; Gherkin authoring completion, rename refactoring, definition navigation, formatting, and feature-language tooling; broad AST/runtime parity; safe typing for Rules, Background callbacks, outlines and multiple Examples blocks; and static inference of expression parameters and transformers. TypeScript content mappers can represent literal scenario and step information today, but those wider integration guarantees need separate implementation and evidence.


## Functional API revision

The current public API replaces callback registration with immutable Effect step values, exact scenario tuples and `run(plan)`, optionally using `plan.pipe(provide(layer))` for external services. The official Gherkin mapper remains reusable. The optional runtime uses Effect 4.0.6, with scenario-local ManagedRuntime state and existing Vitest Cucumber registration inside the adapter. The compiler checks step order/completeness and unmet services as well as literal names. Ordinary string calls retain literal inference; tagged templates do not expose their source text as literal tuple types. Schema decodes interpolated Gherkin captures. See [functional API research and decisions](functional-api.md).

Editor activation was confirmed by the user in a VS Code multi-root workspace after moving the TypeScript SDK/content-mapper settings into the workspace-level `.code-workspace` settings. Folder-level window-scoped settings are ignored in that workspace shape. Broader editor capability claims still require individual checks.

The functional API headless probe also verifies scenario-builder hover, scenario/step completion in TypeScript consumers, consumer errors after an in-memory scenario rename, alias-collision diagnostics and recovery. This is distinct from completion while authoring Gherkin prose.
